# Decisions

How we read the brief, and what we chose where it leaves room. IDs are stable: code, tests, commits and the AI log refer to them. A revised decision keeps its ID and says what changed.

D1–D33 were made in the planning session on 2026-10-22 and 2026-10-23, D34–D39 while scaffolding, D40–D46 in the [design](design.md), D47 while building the UI, and D48 onwards beyond the brief. Requirement IDs (R…) are in [requirements](requirements.md).

| --- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | What "concatenate" means (R1.2)               | A linear chain: the output of step N is the input of step N+1. No branching                                                                                                                                | The brief's example is linear. A graph like a KNIME workflow costs far more and was not asked for                                                                                               |

## B. Transformations

| ID  | Question              | Decision                                                                                                                                                                                                             | Why                                                                                                                                                                       |
| --- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D5  | Replace               | Replaces every occurrence; the match is literal and case-sensitive. Parameters are `old` and `new`, as in the brief. An empty `old` is a parameter error. Case-insensitive replacing goes through Regex replace      | Matches the brief's Python example. With an empty `old`, Python inserts `new` between all characters, which surprises users                                               |
| D6  | Substring             | Python slice semantics, `[start:end]`: zero-based, `end` exclusive and optional, negative indices count from the end, out-of-range indices clamp instead of failing                                                  | The brief's example language, and fewer errors for a no-code user                                                                                                         |
| D7  | What a character is   | What a person sees as one character, a grapheme cluster: 👍🏽, 🇩🇪 and é are never split                                                                                                                                | Java's `substring` counts UTF-16 code units and cuts emoji in half                                                                                                        |
| D8  | "Regex matching"      | Two transformations. Regex extract outputs the chosen group of the first match or of all matches, one per line, and empty text when nothing matches. Regex replace supports `$1` and `${name}`. Flags are checkboxes | The brief does not say what matching outputs, and the output has to be text (D3)                                                                                          |
| D9  | Regex dialect         | Java syntax, validated only by the backend; the error shows the position                                                                                                                                             | Java runs the pattern, and a JavaScript check would disagree on edge cases                                                                                                |
| D10 | Which transformations | First the brief's five plus Regex replace. Then three or four harder ones, each showing something new: case and locale, dates, encodings, line operations                                                            | What is required first, extras after. Refined in step 17: Change case, with Turkish as a language; Line operations; Encode and Decode; Reformat dates (design, section 4) |

## D. Architecture and API

| ID  | Question                                          | Decision                                                                                                                                                                                                                                                                | Why                                                                                                                                                                                                                                                                                                                                              |
| --- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D16 | One service or two (R3.3)                         | One process. The Java library is a separate build module without web dependencies                                                                                                                                                                                       | A network hop on the same machine buys nothing; the module boundary already separates them                                                                                                                                                                                                                                                       |
| D17 | Web API                                           | Spring Boot 4 on Java 25: REST and JSON, OpenAPI with Swagger UI, request errors as Problem Details (RFC 9457)                                                                                                                                                          | The most common choice: reviewers read it at once, and the API can be tried by hand. The developer knows Spring Boot                                                                                                                                                                                                                             |
| D18 | How the backend describes a transformation (R2.1) | Id, name, description, category, and the parameters as JSON Schema: a flat object with string, integer, boolean and enum properties. The frontend has its own small form renderer                                                                                       | The standard KNIME's node dialogs are built on (JSON Forms), without the full library                                                                                                                                                                                                                                                            |
| D19 | How to add a transformation                       | One class in the library and one registration; the frontend stays untouched. A frontend test renders the form of a transformation it has never seen, taken from a test catalog                                                                                          | Direct proof of R2.1                                                                                                                                                                                                                                                                                                                             |
| D20 | Frontend–backend contract                         | Two calls: get the catalog, run a chain. The frontend validates responses with zod. Shared JSON examples run in both the Java and the TypeScript tests                                                                                                                  | Frontend and backend cannot drift apart unnoticed                                                                                                                                                                                                                                                                                                |
| D21 | Limits                                            | Input up to about 100,000 characters, up to about 50 steps, about 2 s per regex                                                                                                                                                                                         | A pathological regex can hang the server (ReDoS). Java 25 already defuses textbook patterns such as `(a+)+$`, but a counted repeat such as `(.*a){30}` still runs for seconds, so the time limit stays                                                                                                                                           |
| D22 | Running it (R4.1)                                 | `docker compose up` as the one-command path, with Spring Boot serving the API and the built frontend; plus a manual path with a JDK and Node                                                                                                                            | A reviewer needs nothing but Docker. | D30 | Java domain model                                 | Sealed interfaces, records and exhaustive `switch` play the role of TypeScript's discriminated unions. Each transformation is a strategy; the catalog is a registry. The library describes parameters with its own types, and the web layer turns them into JSON Schema | The library knows nothing about the web, and errors are data in Java too                                                                                                                                                                                                                                                                         |
| D31 | Module boundaries                                 | The library cannot use Spring: its Gradle module has no Spring on the classpath. An ArchUnit test checks that the server uses only the library's API package and `BuiltIns`                                                                                             | The boundary from D16 is enforced by the build and a test, not by agreement. Revised while scaffolding: the first plan had ArchUnit check the Spring rule as well, but the module boundary already does                                                                                                                                          |

## E. Frontend

| ID  | Question                                    | Decision                                                                                                                                                                                                                                                                                                                                                | Why                                                                                                                                                                                                                                                                                                                                                                                                                    |

Only `<script setup lang="ts">`                                                                                                           | Each layer has its own kind of test, and the split maps onto hooks and presentational components in React. | D27 | Forms from the backend's description (R2.1) | A registry maps each parameter type to a field component, rendered with `<component :is>`. | D28 | UI components                               | shadcn-vue: components are copied into `src/components/ui/` and become our code. Underneath, Reka UI handles accessibility, keyboard and focus; Tailwind tokens handle the look. The transformation picker is a combobox with search, groups and descriptions. Reka UI is checked by reading its source and with probe tests before use                 | Hand-written accessible comboboxes are almost always buggy. Revised: the first plan was plain HTML plus a headless Reka UI combobox; shadcn-vue keeps the same primitives and adds a consistent look. Checked in step 12: probe tests confirmed the combobox (see design, section 7); the copies pass our lint, with two rules relaxed for their folder; the shadcn-vue CLI runs through `npx` and is not a dependency |
| D29 | State                                       | Server state (catalog, run results) lives in TanStack Query, which cancels stale requests through `AbortSignal`, retries, caches and keeps the previous result while the next one runs. The chain being edited lives in a Pinia setup store whose actions call pure functions from `model/`. Only controllers touch stores and queries; views get props | Server state and client state are different problems. Revised: the first plan had no store and a single controller owning all state. Refined in step 13: a query function throws a failed call as an `ApiFailure`, and only an unreachable server is retried, twice. The run's query key is the request itself; a run depends on nothing else, so its cached result never goes stale                                   |
| D32 | Small utilities                             | VueUse: `watchDebounced` for the delay of D11, `useClipboard` for copying the output                                                                                                                                                                                                                                                                    | Standard composables instead of hand-written ones. Revised in step 13: the first plan used `refDebounced`, which keeps its value in a deep `ref`; that wraps the request in a reactive proxy, so the UI could not tell by identity whether the request it sent is the latest one. `watchDebounced` writes into a shallow ref                                                                                           |
| D33 | API mocks                                   | MSW intercepts `fetch` at the network level; the same handlers serve the integration tests and running the frontend without a backend                                                                                                                                                                                                                   | Tests exercise the real request code, not a replaced function. Refined in step 14: the handlers of the tests compute their answers from the request, for Replace and Append, instead of replaying canned responses; the frontend itself always runs against a real API, and running it on the stand-in API was not built                                                                                               |

Rejected for D28: PrimeVue (heavy, with its own theming system), `@knime/components` (its GPL-3 license would extend to our code, and it is an internal API), a plain `select` (no search, no descriptions). Considered for D29: Pinia Colada, a Vue-first alternative to TanStack Query; TanStack Query won because it shares its API with React Query and is better known.

## H. Design

Decided in step 8; the details are in [design](design.md).

| ID  | Question                        | Decision                                                                                                                                                                                                                                                                                                                                                                                           | Why                                                                                                                                                 |
| --- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| D40 | API shape                       | `GET /api/catalog` returns limits, categories and transformations; `POST /api/runs` runs a chain. Identifiers and enum values are lowerCamelCase. Step ids come from the client and are echoed in the response. The top-level `output` is `null` unless every step executed                                                                                                                        | One call gives the frontend everything it needs to build the editor. Echoed ids let the UI keep showing the previous results while the user edits   |
| D41 | Request errors and step results | Problems inside a step (its values, its execution) are step results with HTTP 200. Problems with the request as a whole, including the size limits, are HTTP 400 Problem Details with an `errors` list of JSON pointers, as in the example of RFC 9457. One reader in plain code checks them rather than Bean Validation annotations, because the rules need the catalog or several fields at once | What the user causes by typing is data the UI shows at the field. A 400 means a broken or oversized request, and its pointers still lead to a field |
| D42 | Run rules and status names      | Statuses `executed`, `notConfigured`, `invalidParameters`, `failed` and `notRun` carry the five states of D12. Every step's parameters are checked; execution stops at the first step that is not `executed`, and later valid steps are `notRun`                                                                                                                                                   | All configuration problems show at once instead of one per run. A missing value is a neutral "not configured", not an error                         |
| D43 | Parameter kinds                 | Text, integer, boolean and choice, each mapped to a small JSON Schema subset. Properties are in display order; required means non-empty; an unknown schema renders as a notice, not a guess                                                                                                                                                                                                        | Covers every planned transformation. A JSON Forms UI schema is the next step if groups or conditional fields are ever needed                        |
| D44 | Library structure               | A public API package, and package-private transformations behind `BuiltIns`. Each step runs three stages that return data: generic parameter checks, transformation-specific configuration, execution                                                                                                                                                                                              | The compiler keeps the server away from the implementations, and each stage is tested on its own                                                    |
| D45 | Size caps                       | Text parameter values up to 10,000 characters. No step output above 1,000,000 characters, checked while the result is built, and no run above 10,000,000 characters in all steps together, which bounds the response. The limits can be lowered in tests                                                                                                                                           | Chained replaces can grow a text exponentially, so input limits alone do not protect memory                                                         |
| D46 | Shared contract                 | Example requests and responses live in `contract/`. The server tests compare against them; the frontend tests parse them with the app's zod schemas                                                                                                                                                                                                                                                | One copy of each example, read by both sides (D20)                                                                                                  |

The buttons stay, for the keyboard and for a single tap; the handle is hidden from screen readers. | D55 | Notices              | A run that failed as a whole and a link that could not be opened pop up as toasts at the bottom right, in a stack: the newest in front, older ones peeking out above it, spread out under the pointer or the focus. Each closes after 8 seconds, paused while the pointer or the focus is on the stack; F8 reaches them, a button, Escape or a swipe closes them, and a screen reader hears each once. Each kind has one toast: another message updates it and starts its time again, the same message changes nothing, and a run that succeeds closes it. Reka UI's Toast and its store. The steps still show that they did not run, so nothing is lost when the toast goes. Reka UI, which the UI kit is built on, brings the stack, the timers, the pause and the announcements, so there is no new dependency. Added in step 24, at the developer's request                                                                                                                                                                                                                                   |
| D56 | Working offline      | The built app is a PWA. A manifest with icons lets a browser install it as an app of its own. A service worker, which vite-plugin-pwa has Workbox write at build time, keeps the built files and answers the app's own page from them, so the app opens without the network; any other address, such as Swagger UI or the API, goes to the server. The catalog comes from the server when it answers within 3 seconds, else from the copy kept last time, one per language; on a first visit the app loads it once more when the worker takes the page over. Rejected for D49: the query string, which reaches the server and reloads the page when it changes; compressing the JSON, which gives shorter links but makes reading and writing them asynchronous; short links stored on the server, which need storage.

Rejected for D58: Google Cloud Run, which starts faster but needs a billing account with a card; Koyeb, whose free plan was unclear for new accounts when this was written; Hugging Face Spaces, whose Docker Spaces need a paid plan; reading `PORT` in the server, for the reason above.

Rejected for D57: telling TanStack Query when the page opens that the browser is offline, as `navigator.onLine` says, which it does not do by default, and where a wrong `false` would hold every run though the network is there; a queue of the runs made offline, while only the latest chain matters; a notice that stays until the network is back, which the developer did not want for notices (D55).

Rejected for D56: running the transformations in the browser, either ported to TypeScript, which would give them a second implementation that differs from Java's on regular expressions and dates, or the library compiled to WebAssembly, which adds megabytes and an experimental toolchain; a prompt before a new version takes over, which an app that loads parts of itself later needs, and which here would leave the old version in place on a plain reload until the prompt is answered; a service worker written by hand, which would need the list of built files from the build all the same.

Rejected for D55: Sonner (vue-sonner, shadcn-vue's toasts), a second toast library beside Reka UI's, with a global API that a view does not drive from its props; toasts that stay until they are closed, which the developer did not want; a toast for every failed run, which a server that stays down would turn into a pile of the same message.

Rejected for D54: drag and drop written on the browser's own events, which phones do not fire for a touch and which leave the moving cards and the scrolling at the edges to us; VueUse's `useSortable`, whose default moves the array it is given, while here only the store changes the chain, so it would have added a few lines of lifecycle and a dependency; dragging from the keyboard, since the buttons already move a step from there.

Rejected for D53: a header and a footer that stick over a page that scrolls, which cover a field that takes the focus under them unless every scroll leaves room for them; steps that fill the first column before the second, which would make the chain read down one column and then the other, and move cards across columns at every new step; a fixed header and footer on a phone, where they would leave the chain a strip of the screen.

Rejected for D52: translating the catalog in the frontend, which would then have to know every transformation (D19); ICU4J for its plural rules, a large dependency for one rule; month names in the reader's language in Reformat dates, which would make the same chain give different results to different readers.

## Traps

Edge cases in text. Each one becomes a test.

| Trap                                                                         | Handling                                                                                                             |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Emoji and combined characters: 👍🏽, 🇩🇪, an `e` followed by a combining accent | Count what a person sees as one character (D7)                                                                       |
| Turkish dotted and dotless i; `ß` uppercases to `SS`                         | Case changes use `Locale.ROOT` unless the step picks Turkish or Azerbaijani; the README describes the behaviour      |
| Windows line endings                                                         | Line-based steps accept `\n`, `\r\n` and `\r`, and write `\n`                                                        |
| A date pattern with `yyyy` in strict Java, and 30 February                   | `yyyy` works because the era defaults to ours; strict reading rejects a day that does not exist instead of moving it |
| Sorting that puts `10` before `9` and `é` after `z`                          | Numbers sort by value, text by the collation of `Locale.ROOT`                                                        |
| `+` and spaces in URL encoding                                               | RFC 3986: a space is `%20`, and `+` stays `+`                                                                        |
| Base64 wrapped into lines, and bytes that are not UTF-8                      | Spaces and line breaks are ignored; bytes that are not UTF-8 make the step fail                                      |
| Spaces in parameters, for example appending `" World"`                       | Parameter values are never trimmed                                                                                   |
| `é` written two ways (NFC and NFD), which are different strings              | No silent normalisation; listed among the limitations                                                                |
| Empty input, empty chain                                                     | Every transformation defines its result for empty input; an empty chain returns the input unchanged                  |
| Catastrophic regex backtracking                                              | A time limit per regex (D21); the error comes back as data                                                           |
| `$` in a replacement, for example `"$5 off"`                                 | A clear parameter error at the field, not HTTP 500                                                                   |
| The same transformation twice in one chain                                   | Each step has its own key, separate from the transformation id                                                       |
